## Что я понял про Skills

Skill — это набор правил и инструкций, которые задают агенту понятный порядок работы для определённых задач. Основой Skill обычно является файл SKILL.md, в котором описано, что и в какой последовательности нужно делать. Дополнительно в Skill могут входить скрипты, справочные материалы и другие файлы, необходимые для выполнения его инструкций. Skill сам по себе не делает агента умнее, но делает его работу более упорядоченной, последовательной и предсказуемой. Нельзя считать доказательством только слова агента о том, что Skill был использован. Нужно проверить фактические действия и убедиться, что агент действительно выполнил предусмотренные Skill шаги. Только после такой проверки можно считать, что Skill реально применился и дал ожидаемый результат.

## Где Superpowers могут пригодиться в Axyro

1. При внесении новых изменений в проект можно использовать Skill, который заставляет сначала проверить связанные функции и зависимости, а после изменения — убедиться, что существующая логика не сломалась.

2. При поиске ошибок можно использовать отдельный Skill для последовательной диагностики: сначала найти причину проблемы, проверить связанные части проекта и только потом менять код, а не исправлять его наугад.

3. Для работы с контейнерами можно использовать Skill с безопасным порядком действий: что разрешено проверять, какие команды использовать для диагностики и какие действия нельзя выполнять без отдельного подтверждения.

## Verification Before Completion — практический пример

Для безопасной практики я использовал принцип Verification Before Completion на файле `tooling-review.md`.

Сначала я запустил `git diff --check`, но команда ничего не показала, потому что новый файл ещё был untracked и не участвовал в diff. После команды `git add -N` Git начал учитывать файл в проверке.

Повторный `git diff --check` обнаружил `trailing whitespace` в строке с датой. Я удалил лишние пробелы и снова запустил проверку. После исправления команда завершилась без вывода, то есть больше таких ошибок не обнаружено.

Главный вывод: нельзя считать задачу проверенной только потому, что первая команда не показала ошибку. Сначала нужно убедиться, что проверка действительно охватывает нужный объект, и только после этого делать вывод о результате.

## День 2 — MCP и субагенты

### Что я понял про MCP

MCP — это единый стандарт, через который AI-приложение может работать с внешними инструментами и данными. MCP не является обязательным способом подключения к сервису: например, с GitHub можно работать и без MCP через Git, API или другие интеграции.

Host — это основное AI-приложение, например Codex. Client — часть Host, которая поддерживает конкретное MCP-соединение. Server — сторона, которая через MCP предоставляет агенту данные или возможности.

В MCP я различаю три основных типа возможностей:

* `Tool` — действие или вызываемая функция.
* `Resource` — данные, которые можно получить и прочитать.
* `Prompt` — готовый шаблон постановки задачи модели.

### Что я понял про субагентов

Субагент — это отдельный исполнитель, которому главный агент делегирует ограниченную часть большой задачи. Например, главный агент может заниматься общей архитектурой проекта, а субагенту поручить только найти тесты или исследовать frontend.

Несколько параллельных чатов похожи на работу нескольких агентов, но если я сам создаю их и распределяю задачи, координатором являюсь я. В случае субагентов эту координацию выполняет главный агент.

В моём текущем рабочем процессе Codex я пока не использовал явное делегирование задач субагентам, поэтому не считаю, что эти две практические задачи были фактически выполнены через субагента.

## Границы безопасности и human-in-the-loop

Агент может самостоятельно выполнять безопасные read-only действия: читать файлы, искать информацию в репозитории, анализировать код, находить тесты и конфигурацию, а также готовить предложения по изменениям.

Подтверждение человека требуется перед действиями, которые изменяют внешнюю систему, production-среду или реальные данные. К таким действиям относятся push и создание Pull Request, отправка сообщений, изменение production-базы, удаление данных, миграции, изменение внешних сервисов и другие потенциально необратимые операции.

Главное правило: агент может подготовить действие и объяснить, что собирается сделать, но перед внешним или опасным выполнением человек должен подтвердить его явно.
