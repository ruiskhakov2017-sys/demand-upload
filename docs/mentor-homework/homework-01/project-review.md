# День 5 — Разбор структуры Axyro

## Сценарий

Я разобрал один реальный сценарий Axyro: **синхронизация метрик кампаний группы запуска**.

Главная цель была не запомнить Python-код, а понять, через какие части системы проходит одна пользовательская операция.

## Общая цепочка

Пользователь запускает синхронизацию метрик.

Дальше операция проходит примерно такой путь:

```text
Пользователь
↓
API
↓
создание Job в PostgreSQL
↓
Celery / Redis
↓
Worker
↓
Google Ads Adapter
↓
Google Ads API
↓
Worker получает метрики
↓
данные сохраняются в PostgreSQL
↓
Job получает статус SUCCEEDED
```

## 1. Вход в систему — API

Файл:

`backend/app/api/routes/launch_groups.py`

Endpoint:

`POST /{group_id}/sync-metrics`

Функция:

`queue_metrics_sync()`

Её задача — принять команду на синхронизацию.

Она находит нужную группу запуска, создаёт запись `Job` со статусом `QUEUED`, сохраняет её в PostgreSQL и запускает фоновую задачу через Celery.

## 2. Очередь и Worker

Файл:

`backend/app/jobs/tasks.py`

Функция:

`sync_launch_group_metrics()`

После постановки задачи в очередь Worker забирает её и начинает выполнение.

Job переводится из состояния `QUEUED` в `RUNNING`.

Worker находит кампании, для которых нужно получить показатели, и выбирает подходящий Google Ads adapter.

## 3. Выбор Adapter

Функция:

`_status_adapter()`

Если Axyro работает в режиме `SIMULATION`, используется:

`MockGoogleAdsAdapter`

Он имитирует Google Ads и позволяет работать без реального обращения к Google.

Если используется реальное Google-подключение, вызывается:

`build_google_ads_adapter()`

Файл:

`backend/app/google_ads/service.py`

Эта функция получает настройки Google-подключения, проверяет их и создаёт adapter нужной версии Google Ads API.

Например:

* `v24.2` → `GoogleAdsV242Adapter`
* `v25` → `GoogleAdsV25Adapter`

## 4. Получение данных из Google Ads

Реальная реализация находится, например, в:

`backend/app/google_ads/versions/v24_2/adapter.py`

Функция:

`fetch_campaign_performance()`

Она обращается к Google Ads и получает за последние 30 дней:

* показы (`impressions`);
* клики (`clicks`);
* расход (`cost_micros`);
* конверсии (`conversions`);
* ценность конверсий (`conversions_value`);
* статус и название кампании.

Для меня важно не запоминать синтаксис этой функции, а понимать её роль:

**Adapter — это слой, который знает, как Axyro должен разговаривать с Google Ads.**

## 5. Сохранение результата

После получения данных Worker сохраняет текущие метрики в `CampaignInstance`.

Также создаётся `PerformanceSnapshot` — отдельный снимок показателей кампании.

После успешной обработки:

* Job получает статус `SUCCEEDED`;
* создаётся `JobEvent`;
* создаётся `AuditLog`;
* изменения сохраняются в PostgreSQL.

## Две разные карты одной системы

Во время разбора я понял, что важно не смешивать две разные схемы.

### Инфраструктурная карта

Она отвечает на вопрос:

**Где что работает?**

Например:

```text
API container
Worker container
Redis
PostgreSQL
```

### Логическая карта

Она отвечает на вопрос:

**Что происходит с конкретной командой?**

Например:

```text
API
↓
Job
↓
очередь
↓
Worker
↓
Adapter
↓
Google Ads
↓
сохранение результата
```

Несколько Python-функций могут выполняться внутри одного контейнера. Поэтому каждый новый файл или функция не означает отдельную программу или отдельный контейнер.

## Что я понял

Мне не нужно запоминать Python-код как формулы.

Для моего текущего уровня важнее понимать роль частей системы:

* **endpoint / route** — место, куда приходит команда;
* **PostgreSQL** — долговременное хранилище данных;
* **Job** — запись о работе, которую система должна выполнить;
* **Redis / Celery** — механизм очереди фоновых задач;
* **Worker** — исполнитель задачи;
* **Adapter** — прослойка между Axyro и внешней системой;
* **Google Ads API** — внешний источник реальных данных.

Главный вывод Дня 5:

**Axyro состоит из частей с разными обязанностями, а одна пользовательская операция может пройти через несколько таких частей. Мне важнее понимать этот маршрут и ответственность каждого слоя, чем запоминать конкретный синтаксис Python.**

## Возможное архитектурное улучшение

Функция `queue_metrics_sync()` в route выполняет не только приём HTTP-запроса, но и часть orchestration-логики:

* создаёт Job;
* проверяет повторный запуск;
* записывает audit;
* сохраняет изменения;
* ставит фоновую задачу в очередь.

Возможное улучшение — вынести эту логику в отдельный service, оставив route более простым:

```text
route
↓
service
↓
остальная логика
```

Это не означает, что текущая реализация неправильная. Это возможный способ сделать разделение ответственности более явным.
